# Tang as a plugin in a DAW

Part of what `CLAUDE.md` holds as a front door: the plugin that Tang is in a DAW (step 113), which is built from the same library as the `tang` program. `CLAUDE.md` has the index of the reference files. The `TODO:` lines are where this is not done yet.

### The two plugins in `Tang.clap` (step 113, `tang-clap/`, `tang::embed`)

The user's ask, after the plugin's own window (step 112) was done: "would be possible to add a target to be able to build this as a VST or other plugin format that we can load into a daw?" (2026-11-05), and, asked which DAW: **"I mainly use bitwig, on windows, so thats where I want to try it. Lets try this next."** (2026-11-06). Bitwig loads CLAP natively and co-created it, so CLAP is the format; VST3 and AU would come from wrapping it (`clap-wrapper`), and are not built.

- **What the file has.** One file, `Tang.clap`, with two plugins in it: **Tang** (`io.github.apanloco.tang.instrument`; features `instrument`, `synthesizer`, `stereo`: notes in, what the session plays out) and **Tang FX** (`io.github.apanloco.tang.effect`; `audio-effect`, `stereo`: stereo audio in, what the session makes of it out). The ids are what a host keeps a plugin by in every project that has it: **they are never changed.** Both have a stereo output, one input of notes (the MIDI dialect is the preferred one, the CLAP dialect is understood: a note-on and a note-off, and a choke as a note-off; what a CLAP note says beyond that, its expressions, is not carried over) and a window; the effect has a stereo audio input as well.
- **What a new one is.** A new Tang is one lane with the oscillator (`builtin:osc`) and a new Tang FX is one lane with the audio input (`builtin:input`, which plays what the host gives the plugin to hear: no sound card is opened) that goes to the mix, so that it passes the sound through until a person builds something in the page. **The master's limiter is out of the sound in both** (`Kind::default_session`): a host works in floating point and has headroom, and the limiter holds the sound back by 2 ms, which a host that is not told of it cannot make up for (an effect would be late against its own dry sound). A person who wants it puts it in, in the page, and then has the 2 ms.
- **The window is the page** (step 114). A host that can put a plugin's face in a window of its own (that is what the format's embedded window is for, and Bitwig supports it: the user tried it in Bitwig on Windows on 2026-11-09, "it works well") is given **an embedded window**: `create` for the system's own API (`win32` on Windows, `cocoa` on macOS), `set_scale`, `get_size` (1100 x 720, a window that can be resized both ways between 480 x 320 and 16,384 a side), `set_parent` with the host's window, `show`; and the window is **a web view of the system** (WebView2 on Windows, WKWebView on macOS, through `wry`) at the address of the page of that instance (`http://127.0.0.1:<port>/`), which the plugin makes in the host's window and the host sizes. Every instance serves its own page on a port that the system picks, on this machine only (no token is needed there). Where the system has no web view for it (Linux; a Windows that has no WebView2 runtime) the window is **a floating one that the plugin shows itself**, as it was in step 113: `show` opens the page in the browser that the person has, `hide` does nothing, the address is in the log (`Web interface: …`) if nothing opens it, and `TANG_BROWSER` says another program to open it with (it is run with the address as its one argument). A host is given the one that it asks for (`is_api_supported`: a floating window on every system, an embedded one where there is a web view), and the one that the plugin would rather be asked for (`get_preferred_api`) is the window of the host's where there is a web view. The plugin also has **a parameter**, **Open the page** (below), which opens the page in the browser in any case: for a host that shows no window button, and for a person who wants the page in a browser tab as well.
- **The web view (`tang-clap/src/gui.rs`).** The order of the calls, the sizes and what the view shows are written against two small traits (`Maker` and `View`), so that tests with no window hold them (`Gui`: the calls in the order that a host makes them, the size that the host made the window, the scale, the page that the view shows and follows); `native` is the system's web view through `wry`, the one part that needs a screen. *A window that is asked for before the plugin is switched on* (a host starts a plugin when it is going to play it, which may come after a person opens the window) **shows a few words that say that Tang has not started, and gets the page when the instance has one**: `refresh_gui` after `activate`, and after a session that the host gives (which has the instance served at another address: the view goes there); a view that cannot be made says why in the log and is tried again at `show`. *Sizes:* a host counts **pixels on Windows and tells the plugin the scale** (`set_scale`: 1.5 for 150%) and points on macOS (which the system has scaled already), so the default size is scaled where it is pixels (1100 x 720 at 150% is 1650 x 1080, which is the room that the page has at 100%), the least size is scaled too, and a size that the host has made the window is what it is. *Found with wry 0.57:* a view on macOS asks its parent for its window and **panics if there is none**, so the plugin asks AppKit first (`ready`), makes the view at `show` if the host has not put its view in a window yet, and guards every call into wry (a panic is an error, not the end of the host's process); a view that is **focused** makes the program that holds it the active one, which the host's window is not Tang's to say, so the view is made unfocused, and it **accepts the first click** (a click on a window that is not the key one is for the page); WebView2 keeps its profile in a folder that is by default beside the program that uses it, a host's own directory that a person cannot write to, so the plugin gives it `%LOCALAPPDATA%\Tang\WebView2`. *Found with clack at the pinned commit:* its wrappers of `set_parent` and `set_size` answer `true` to the host **whatever the plugin returns** (the `is_ok()` inside is lost to an `is_some()` outside; `create`, `show` and `hide` are right), so a view that cannot be made is told to the host at `show`, which is right, and not at `set_parent`; the plugin says why in its log.
- **What is saved is the session.** The host's `state` is the session as the text of a session file, after nine bytes (`TANGSESS` and a version, 1) that say what it is: what a person builds in the page (lanes, effects, cables, modulators, a macro's name, the places of the nodes) and what the plugins inside keep in them (step 112, part C) go with the host's project and come back with it. State that has no magic and is text is taken as a session file as it is (a person can paste one into a project); one of a later version is refused with the reason. A project whose session **cannot be loaded here** (a plugin that is not installed on this machine, a file that is not a session) gets a **new session in its place, and is saved as what it was given for as long as nothing in the new one is changed**: a project that is opened and saved on a machine that lacks a plugin does not lose the session.

#### How it is built

```
host's main thread ── Host ───────────────── activate / session_text / set_session_text / url
host's audio thread ─ Audio ── process(midi, input, output) ──► Renderer (Mutex) ──► AudioGraph ──► plugins inside
idle thread ───────── looks every ≥ 20 ms: no block since the last look? ─► Renderer::idle (takes the commands)
controller's thread ─ Controller + Runtime (the page's server) ◄── what the page asks, and Host's questions
```

- **The library and the plugin.** The package is a library (`src/lib.rs`: everything that `main.rs` held; `run` is its one public function besides the module `embed`) and a thin binary (`src/main.rs`: it ends the process). The plugin is a crate of its own in the workspace, `tang-clap` (a `cdylib` and an `rlib`; `clack-plugin` for the CLAP side, the library for everything else), so that a plain `cargo build` does not link a plugin. The channels between the audio thread and the rest are made in one place for the program and the plugin (`app::wiring::Wiring`). **The clack crates are pinned to one commit** (`rev = "57e89b3…"` in both manifests): the newest commit of the repository changed the host's API, and adding a new crate from that source had moved the lock to it without a word.
- **`tang::embed`.** `Host` is what the host's main thread has, one for each instance: `activate(rate, max_frames)` makes the engine (the renderer, the idle thread, and the controller's thread, which loads the session and serves the page) and gives the host's audio thread its end of it (`Audio`); `session_text` asks the controller's thread for the session as text (it reads out what is in the plugins inside first, as a save does: `Controller::session_text`); `set_session_text` is a session that the host gives. Activated again at the rate and the block size that it has, nothing is made again (what the page was editing goes on); at another, the session is read out and loaded again, since the plugins inside are loaded for a rate and a size. **A session that the host gives while the plugin plays is loaded under the handle that the audio thread already has** (the new engine takes the place of the renderer inside the same mutex), with the page going to another address.
- **The audio thread.** `Audio::process(midi, input, output)` puts the host's input where the audio inputs of the session read it (`HostInput`), has the renderer render the block with the host's events at their frames after the notes that the page played (`Renderer::render_planar`), and copies the engine's two channels into the host's buffers (a host that gives one channel has the left, one that gives more has the right again). It `try_lock`s the renderer and spins for a few microseconds at most; a block that cannot have it is silence. The plugin copies what comes in before it writes what goes out, since a host may give the input and the output as the same memory. **A block of no frames** is not a block: it is not rendered (the plugins inside are never given one), it is not counted for the idle thread (it takes no commands, so the idle thread goes on taking them), and the events that came with it are dropped, since they have no frame to be at (`Audio::process`); a block that has no audio port to play on is an error that the host is told of.
- **The idle thread.** The commands that the controller sends go through a channel that holds 64, and the controller waits for room in it when it is full; a host that is not calling `process` (a track that is switched off, an audio engine that is stopped, and `activate` itself, which loads the session before any block is asked for) would stop a page that is editing. A thread looks every 20 ms or two blocks, whichever is longer, whether a block has come since the last look, and if none has, has the engine take what is waiting (`Engine::idle`: the commands, the plugins that come and go, and the notes that the page played are dropped: they are not for a block that comes later).
- **The host is a source of notes.** What the host sends is the first MIDI device (`Source::device(0)`), which the controller calls `Host` (`embed::HOST_DEVICE`; a `DeviceWatcher` that has the one device), so that a lane can be wired to it, or not, as to any device; the page's own piano and keys are the keys' source, as ever.
- **The page.** The controller's thread serves the session as `tang serve` does (`web::runtime::Runtime`), on `127.0.0.1` and a port that the system picks. **A plugin's own window is not available inside a host** (`Controller::window_check` says why; the main thread is the host's), and **the catalog lists the built-ins and the modules of the library at once, and the installed plugins only if `TANG_SCAN` is set** (a scan loads every installed plugin on a thread of its own and lets go of it, and a host's main thread turns the run loop all the time: a plugin of the JUCE kind that is loaded and let go of while it turns takes the process with it, f179. **Found again with the window**: `tang window Tang.clap` died in `juce::MessageQueue::runLoopSourceCallback` when the page, opened in the window, started the scan, which in step 113 it did when the first browser had come. A plugin does not scan by itself now; with `TANG_SCAN=1` in the host's environment it does, as it did, at that risk). Nothing opens a sound card or a MIDI port, installs a Ctrl+C handler, or turns the main run loop. **A page that cannot be served** (the system gave no port) **does not stop the plugin**: the controller's thread goes on without one (the session plays, and is the host's to keep), the log says why, and the window button and the switch below answer that there is no page.
- **The switch that opens the page.** The plugin's one parameter (`PAGE_PARAM`, id 0: **Open the page**, stepped, 0 or 1, automatable, shown as `Closed` and `Open`). A press is the host setting it from under a half to a half or more (setting it again to what it is, is not one, so that an automation lane that stays at 1 opens nothing more). **In a block** the audio thread sees it and opens nothing (a browser is not started on the audio thread): it asks the host to call the main thread back (`request_callback`), and `on_main_thread` opens the page and has the switch put back to 0, in the next block, as a `param_value` event in the block's output (the host shows it fall). **In a flush** (the host sets parameters while the plugin is not processing, on the main thread, or only wants them taken) the page is opened at once and the switch goes back at the end of the same flush. A press while the plugin has not started opens nothing, says why in the log, and the switch goes back all the same. Every instance opens its own page.
- **The parameters that follow the macros (step 117).** *The user, shown "Bitwig cannot automate or modulate anything of what a person builds": "yes all on 3 is very relevant".* After the switch the plugin has **16 parameters, ids 1 to 16** (`tang::embed::SLOTS`, `FIRST_MACRO_PARAM`: **never changed**, a host keeps automation by them), a macro to each **in the order of the session** (the first macro of the file is the first parameter, `Controller::macros`; every macro has one whether the box of its module shows its knob or not, and the seventeenth and the ones after it have none). A host wants a list that does not change while a plugin is on, so **every slot is a parameter whether a macro is in it or not**: `Macro 3` where none is and `Macro 3: Brightness` where one is called that (module `Macros`, 0 to 1, automatable and modulatable, `0.50` as text, and a typed `0.5` or `50%` is read). *What the host sets*, a value in a block (or in a flush) or the modulation of a parameter (`PARAM_MOD`: the amount that Bitwig's modulators add), is written by the audio thread into a cell for each slot (`HostParams`: a number and its sequence number in one word, no lock and no queue, so the newest is the one that is taken and a host that sends a hundred values while the controller is busy is taken once) and rings a bell that wakes the controller's thread, which takes it (`Bank::sync`): **a value is the change of a macro that a knob makes** (`Controller::set_macro_from_host`: the model, the engine and every client, as `SetModulatorField` of a macro is) **with no step of the history** (an automation lane would fill it and empty Redo) **and the session not marked as changed**, and **a modulation is added to what the engine plays and goes to the engine alone** (`set_macro_in_engine`, held to 0 to 1: what the page shows and the project keeps is the value that was set, as a knob that a modulator moves is shown at its own value). A value that the host sets is in the sound after the controller's wake and the next block (a block or two), not at the frame that it was sent for. *What the page changes* (a knob on a macro's node, Undo) is found by `sync`, which runs after every request that a page made and every 50 ms, and is told to the host by the audio thread in the next block **as a gesture**: `PARAM_GESTURE_BEGIN`, the value, and `PARAM_GESTURE_END` when the knob has been let be for 0.3 s (what a host records automation from; a macro that the host itself has just set is not told back to it). *What the host is to read again*, the names, which slot has a macro and the values of the slots whose macro is another one now, is asked for with `params.rescan` (`INFO`; `VALUES`, which a host does not record as automation) on the host's main thread, which the controller's thread has called back (`request_callback`, as for a page that opens another session) when a macro is made, taken out or called something and when a session is loaded. The bank is made again with the session and takes nothing of what the host set for the one before it, and the audio thread, which is made again when the plugin is activated, says nothing of what the page changed before it was.
- **The host's tempo and beat (step 118).** *The user's "yes all on 3": the tempo came after the parameters.* A host that says its tempo (`transport.tempo`, with `HAS_TEMPO`) **is the tempo of the session**: the audio thread gives it to the engine in every block (`Audio::process_at`, `Renderer::set_host_time`, `AudioGraph::set_host_time`: the graph's tempo from that block on, with none of the controller's wait, so that everything that follows the tempo, a synced LFO or step sequencer, goes by the host's, and by it as it moves in a ramp) and writes it, only when it changes, into a cell and rings the bell, and the controller's thread takes it (`Bank::sync`, `Controller::set_bpm_from_host`: the model and every client, as `SetBpm` does, **with no step of the history, the session not marked as changed and nothing for the engine**, since a command from the controller would come after a newer tempo and put the old one back for a block). From the first tempo that a host says the session's tempo is the host's (`Controller::host_tempo`, `meta.hostTempo` on the wire): **a tempo that anything else sets (the page, `SetBpm` from another client) is put back at the next look**, and the page's bar shows the tempo as the host's number and not as a field (`app/Tempo.tsx`), as a session that has heard of no host (a program that is not a plugin, a host that says no tempo) shows it as a field, as it always did. A session that is made later (a project that is opened, `Open…`) is given the tempo that the host said last (the host says one only when it changes). **While the host plays and says where it is** (`IS_PLAYING` and `HAS_BEATS_TIMELINE`: its beat, `song_pos_beats`), **an LFO or a step sequencer that follows the tempo and does not start again with a note is where the beat says**: the phase is the beat, at the end of the block, divided by the length of a cycle in beats (a step, for a step sequencer; `Modulator::tick_at`), so that its cycle begins on the host's beat, it goes along when the host jumps or loops, a random wave draws the number of the cycle that the beat is in (the one that it drew the last time that beat came) and two instances in one project that follow the same note length are one wave. An LFO or a step sequencer that **starts again with a note** (`retrigger`: a step sequencer does to begin with, an LFO does not), one that **has a rate of its own** (`sync` free) and any other modulator are as they were: they go by themselves, at the host's tempo if they follow it. While the host is stopped, or says no beat, everything goes by itself at the host's tempo. The recorder and the player of patterns do not follow the tempo (a TODO of `session-file.md`: a recording is made at the host's tempo, since it is started with the session's).
- **The file stays loaded (Windows).** The plugin starts threads (the idle thread, the controller's, the page's server) that can still be running a moment after the host has let go of the last instance, and a host that unloads a plugin's file when it has no instance of it takes the code of those threads away with it: the file pins itself in the process when the host loads it (`pin_library`: `GetModuleHandleExW` with the `PIN` flag), so that a thread that outlives its instance never runs code that is not there. The other systems have no pin (it is a no-op there).
- **The plugins that Tang hosts are told the tempo (step 120).** *The user's "lets also listen to the daws BPM and also propagate it to any synths we use": the first half was step 118, which makes the host's tempo the session's; this is the rest.* Every plugin that is in the session, the instrument of a lane, its effects and the effects of a group's bus, is told **the tempo that the graph goes by** before each block (`Plugin::set_tempo`, called for all of them from the top of `AudioGraph::process_events`, after the commands and the host's time: a plugin that comes in later is told at its first block, and a tempo that is not a finite number above 0 is not told). So **in Bitwig it is Bitwig's tempo that reaches a synth that is inside Tang**, and in a program that is not a plugin it is the session's: until then every VST3 plugin was told 120 whatever the session's tempo was, and every CLAP plugin was told none. *What a format makes of it:* a **CLAP** plugin is given a transport in each block (`transport_event`: `HAS_TEMPO` and the tempo, and no other flag and no position: Tang does not tell a plugin that it plays, since it does not know; a plugin that has not been told a tempo yet is given no transport, as it was); a **VST3** plugin's process context says, as it always did, that it plays and that the tempo is valid, with the tempo that it was told in place of the 120 (`process_context`); **an LV2 plugin is told nothing** (it would take `time:Position` atoms in its event sequence). **The beat is not passed on, nor whether the host plays, a loop or the time signature**: a hosted plugin that locks to the song position runs by itself at the tempo.
- **The log.** A host has no terminal, so the plugin logs to a file: `tang-plugin.log` in the system's directory for temporary files (`%TEMP%` on Windows), shared by every plugin in every process (each line says which process wrote it), begun again when it is over a megabyte. The level is `RUST_LOG`'s, or info.

#### Building it and putting it where a DAW looks

- **Windows (Bitwig).** With Rust and Node installed: `cd web && npm ci && npm run build` (the page is what a release build embeds), then `cargo build --release -p tang-clap --no-default-features --features vst3` (the plugins that can be loaded inside Tang are VST3 and CLAP; LV2 needs a library that Windows has not). The library is `target\release\tang_clap.dll`; **copy it as `Tang.clap`** to `C:\Program Files\Common Files\CLAP\` (all users; needs administrator rights) or `%LOCALAPPDATA%\Programs\Common\CLAP\` (one user), and have Bitwig rescan (Settings → Plug-ins → Rescan, or restart it). The CI job `plugin` builds the same file on `windows-latest` and keeps it as the artifact **`Tang-clap-Windows`** (`Tang.clap`), the one to download when there is no Rust on the machine; it has the same job for macOS and Linux. Building should need nothing more for the window (`wry` links the loader of WebView2 itself; it was type-checked and linted for Windows from the Mac, and the CI job `plugin` has built it on `windows-latest` (its first run, 2026-11-06, on the fork's branch: the file builds and the plugin crate's tests pass there), and the user ran the file that it built in Bitwig on Windows on 2026-11-09 and said that it works well, with its window; **running** it needs the WebView2 runtime (see Using it in Bitwig).
- **macOS.** `cargo build --release -p tang-clap`, then `tang-clap/bundle.sh release` makes `target/bundle/Tang.clap` (a bundle: a directory with the library and an `Info.plist`, **signed ad hoc**: a signature of no identity, which is enough for the Mac that built it), and `mkdir -p ~/Library/Audio/Plug-Ins/CLAP && rm -rf ~/Library/Audio/Plug-Ins/CLAP/Tang.clap && cp -R target/bundle/Tang.clap ~/Library/Audio/Plug-Ins/CLAP/` puts it where a DAW looks (remove an older copy first: macOS can kill a signed binary that is written over in place; the system's folder, `/Library/Audio/Plug-Ins/CLAP/`, needs administrator rights). Tang's own `tang enumerate plugins` lists both plugins from there (under `CLAP Plugins`, with the ids `io.github.apanloco.tang.instrument` and `io.github.apanloco.tang.effect`), and a session can say `plugin = "clap:io.github.apanloco.tang.instrument"`. The page of a plugin that is loaded in a host scans the installed plugins when its first browser has come, and so meets this file, which the host has loaded already: clack counts the calls of `init`, so that it is loaded once and let go of once more, which was checked by hand (the plugin inside Tang, found by its id, with the scan on: the catalog came back whole with `Tang` and `Tang FX` in it, and nothing was lost). A bundle for another Mac needs a signature with an identity and to be notarised (a Mac that is strict about plugins will say so). The library is for the architecture of the Mac that built it (arm64 here): a host that runs as x86_64, under Rosetta, cannot load it, and a universal one is two builds put together with `lipo` (not done). No DAW is installed on the Mac that this was built on, so it was not tried in one.
- **Linux.** The same, and `~/.clap/`.
- `tang describe /path/to/Tang.clap` loads the file as any CLAP plugin and says what it is, and a session whose `plugin` is that path plays Tang inside Tang (the file's first plugin is the instrument): the check that needs no DAW.

#### Using it in Bitwig

Put **Tang** on an instrument track (or **Tang FX** in a device chain) and press the device's button for its window (the little window icon: the plugin asks for an embedded window, which Bitwig shows a button for, as for every plugin that has one: the user tried it, 2026-11-09): Tang's page opens **in the host's window**, 1100 x 720, which the host can resize. Build there what Tang builds (the bar's `+ Lane`, effects, modulators, cables, modules), play notes from a clip or a keyboard (the page's own piano has its keys shut to begin with, step 119: the `Keyboard` button in the bar at the bottom opens them), and save the project: the patch is in the project. Two instances in one project are two sessions with two pages. **The window needs the WebView2 runtime on Windows** (Windows 11 has it, and Windows 10 where Edge is up to date; Microsoft's "Evergreen" installer otherwise): without it the window is the page in the browser, which the button opens. **`Open…`** in the page's bar (step 115, part A) picks a session file (`.toml`) from the disk and makes it the session of this instance: the engine is made again with it, the window follows to the page's new address, and the host is told that the project has changed (`state.mark_dirty`), so that it is saved with the project; there is no undoing it. With libraries of sounds to list (below) it opens the picker instead, which has that chooser among its own.

**The picker of sounds** (step 116, "a more advanced loader/picker"): `Open…` opens a box that lists the sounds Tang can see, a section for each library, with a search, the arrow keys and Enter, and **From this computer…** for a file anywhere else. The libraries are the folder that sessions are saved to (`~/.config/tang/sessions`, or `%USERPROFILE%\.config\tang\sessions` on Windows, listed as **Saved sessions**) and the folders that `~/.config/tang/config.toml` names, one table for each:

```toml
[[sounds.folder]]
name = "Examples"            # optional: the folder's own name if it is left out
path = "~/tang/examples"     # a leading ~ is the home
```

The file is read each time that the plugin starts its session (a project that is opened, the plugin activated again, a sound that is opened), so a folder that is added is there the next time and not at once; a file that cannot be read, or has a table that is wrong, is left out with a note in `tang-plugin.log`, and the plugin plays. A folder is listed down to four folders deep, its `.toml` files, newest first; a file that is not a session is shown, greyed, with why. The page names no path: a sound is named by its library's id and its place inside it, and a file that a link leads out of the folder is not read. A library that is far away (a server that people upload sounds to, which Tang downloads from) is one more kind of library and not built (the TODO in `web-page.md`, step 116).

**`Open the page`**, the device's one parameter (set it to on, or click it in the device's parameter list or the remote controls page), opens the page in a browser tab in any case, and falls back to off. If nothing opens a page, its address is in `tang-plugin.log` (`%TEMP%\tang-plugin.log` on Windows), and the same file says when the window's web view was made and when its page had loaded (`The window's web view is made`, `The window's page has loaded`).

**The macros are the device's parameters** (step 117): `Macro 1` to `Macro 16` in the device's parameter list and on its remote controls page, in the order of the macros in the session (one that is called something is `Macro 2: Brightness`). Automate them, or modulate them with Bitwig's own modulators: the page's knob shows the value that was set, and what is played is that value and the modulation. A macro that is made, called something or taken out is read again by the host while the plugin is on (**not tried in Bitwig**: the user's hand).

**Without a DAW, on a Mac:** `tang window ~/Library/Audio/Plug-Ins/CLAP/Tang.clap` opens the plugin's window by itself, in a window of Tang's own, as a host would (`--size 900x600` makes it that size once it is open, `--snapshot FILE` writes what is in it as a picture, `--tree` prints the views).

- **A web view on macOS panics for a parent that is not in a window**, in wry 0.57 (`ns_view.window().unwrap()`), and the host's window may not be one yet when `set_parent` comes: the plugin asks AppKit and waits for `show`.
- **clack's `set_parent` and `set_size` always say yes** (see "The web view"): found by a test that gave the plugin a window of another system's kind and saw the plugin refuse it in its log and the host not be told.
- **clack's `as_core_event` does not know the gesture events** (step 117, found by a test that saw the event that the plugin had sent and could not read it): at the pinned commit `CoreEventSpace` has the variants `ParamGestureBegin` and `ParamGestureEnd` and `from_unknown` never returns them, so a host written with clack (the test host here) reads a gesture by its type (`UnknownEvent::as_event::<ParamGestureBeginEvent>()`); the plugin sends them, as the format says, and a host that is not written with clack reads them as it does every other event.
- **A first draft of the bank would have applied a value that the host set for an empty slot to the macro that came to it later, and would have left the old names on a new session that has no macro** (step 117, found by reading the draft before the first test of it ran, and held by a test of each now): the loop went over the macros and not over the slots, and the names were published only when the macros were not what they had been.
- **The standard library's `fetch_update` is deprecated by the toolchain of the day** (`try_update`: it has been renamed): the cell that the audio thread writes is a compare-exchange loop, which is the same on every toolchain, takes nothing from the allocator and waits for no one.
- **`#[ts(optional)]` is for an `Option` only, and a `bool` that is left out of the wire says `ts(as = "Option<bool>", optional)`** (step 118, found by the build of `Meta.host_tempo`: the pattern is `takes_notes`'s and `has_editor`'s, and is what the generated type `hostTempo?: boolean` comes from; `TANG_UPDATE_TYPES=1 cargo test --features web typescript` writes it).
- **A tempo above 0 is never the 0 that a cell that nobody has written holds**, so that the first tempo that a host says is always a change and the cell needs no sequence number to know it is the first (a first draft had `sequence == 0 ||` in the test, which the mutants showed to be dead).

- **Before step 120 the session's tempo did not reach any plugin that the session holds** (step 120, found by reading what the adapters pass to a plugin): the VST3 adapter's process context said `tempo = 120.0` as a constant, whatever the session's tempo was, and the CLAP adapter passed no transport at all, so the tempo-synced parts of a hosted synth, in a program that is a plugin or not, ran at 120 or at their own.
- **`tang::plugin` is private, so the host's side of CLAP is tested in the library** (step 120): with `clack-plugin` and the plugin side of `clack-extensions` as dev-dependencies (the same revision as everywhere) and `clap::load` split into finding a bundle and `load_found`, which a test hands a bundle that is in the program (`PluginBundle::load_from_clack`).
- **A first draft of the probe covered one of the host's two calls of `process`** (step 120, found by writing the mutants): a plugin with no audio input goes through one and every effect through the other, so a mutant of the second would have passed; the probe has an effect flavour that declares an input port.

#### Decisions (D113; the user may overrule them)

(1) CLAP first, both an instrument and an effect in one file, with ids in the `io.github.apanloco` namespace. (2) The window is the page in the browser first; a webview in a window of the host's is a step of its own. (3) The master's limiter is out in a new plugin (2 ms of latency that cannot be told to the host). (4) The session is the state, as text, so that a project can be read by a person and by a later Tang. (5) The host is a device called `Host`, not the keys. (6) The scan of the installed plugins waits for the first browser. (7) No parameters of the session in the first version: the plan is the macros, and a first version that can be tried is worth more than one that has everything; the one parameter there is, **Open the page**, is there because it is not known that Bitwig shows a button for a window that the plugin shows itself, and every host shows the parameters. (8) The clack crates are pinned. (9) A block of no frames is not a block (not rendered, not counted, its events dropped): the simplest thing that cannot go wrong, until a host is known that sends notes in one. (10) The file pins itself in the process on Windows only, which is where it will be tried first; the other two systems wait for a reason. **Step 114:** (11) The window is a web view in a window of the host's where the system has one (WebView2, WKWebView through `wry`: +121 crates in the lock, and `objc2` went from 0.6.3 to 0.6.5), and the page in the browser where it has none; the browser stays as a fallback and as the parameter `Open the page`. (12) A plugin does not scan the installed plugins by itself (f179): the built-ins and the modules are listed, and `TANG_SCAN` opts in. (13) A window that is opened before the plugin is switched on waits with a page that says so, and gets the page when there is one. (14) `tang window` opens a CLAP plugin's window, as a diagnostic. **Part C** (the user: "can you install it? I still cant open the UI"): the button on a CLAP node of a session opens it too, through the registry of the windows that the VST3 plugins have (the editor keeps a main-thread handle of the plugin, which is on the audio thread, and a token that says whether the plugin is still there); `tang window` and a session are one path. (16) **`Open…` replaces the whole session of the instance and asks nothing first** (step 115): there is no undo for it and no confirmation (`window.confirm` is not a thing that every web view has, and a refused one would make the button do nothing), and a program that is started with its file does not offer it (it would have to be made again from the outside: a restart of the engine, the controller and the server in one process; written down as a TODO). **The size is a decision too**: the page sends the text as one message, so the server reads up to 8 MiB from a connection that has been let in (the page says 4 MiB), where a connection that has not been is still cut at 64 KiB the moment its message is read (the transport reads a frame whole, so that is held in memory for a moment: up to 8 MiB for each of at most 32 connections, before the token). (15) A plugin that asks the host to hide its window has it closed (and made again when a person asks), and one that asks to show it is refused: a window is opened by a person.

**Decisions of step 117 (D117; the user may overrule them).** (1) **Sixteen parameters**, a constant (`SLOTS`) that can grow by adding ids after the last. (2) **A macro is a parameter by its place among the session's macros** (the order of the file), not by a number that it keeps: the number would have to be in the file or in the plugin's state, and a sound that is opened with `Open…` would bring its own numbers into a project that has automation on the ones it had; this way the first macro of any sound is `Macro 1`, and the cost is that taking a macro out moves the others up (a TODO). (3) **Every macro has a slot**, whether the box of its module shows its knob or not (`expose` is about the box). (4) **The host's value goes through the controller** and not straight to the engine: one ordered path, no old value that comes back after a new one, and the engine's place for the macro (a position in a rack that moves when modulators are added or taken out) is found by the controller, which owns it; the cost is a block or two. (5) **No step of the history and no mark on the session** for what the host sets: playing a project is not editing it. (6) **A modulation goes to the engine alone**, the page and the file keep the value that was set. (7) **Every slot is listed, a macro in it or not** (not hidden when empty): a host that did not read the list again when a macro is made would otherwise never show it, and the sixteen are a common sight in a plugin that has macros. (8) **A gesture is the knob's, ended by 0.3 s of quiet** (the page has no notion of a hand let go of), and a value that comes from Undo is told the same way (a session that is opened is not told as a gesture: the host reads its values, `VALUES`, which it does not record). (9) **The host is asked to read again with `INFO` and `VALUES`**, and not with `ALL`, which needs the plugin to be switched off.

**Decisions of step 118 (D118; the user may overrule them).** (1) **The host's tempo is the session's, always**: not a switch between the page's tempo and the host's, since a tempo that is typed in a plugin and then not followed by a synced LFO is a surprise at a gig, and a host that says a tempo is the clock of the project; a session that has heard of no host, and a host that says none, keep the field. (2) **The engine has the tempo from the audio thread, in the block**, and the controller has it for the model and the clients, with nothing sent to the engine: two paths for one number, because the one through the controller is a block or two late and would put an old tempo back over a newer one. (3) **Beat lock is for an LFO or a step sequencer that follows the tempo and does not start again with a note, while the host plays**: a note that starts it again is the person's say (key sync), and a rate in hertz is not the tempo's; a step sequencer starts again with a note to begin with, so a new one is not on the grid until it is told not to (the retrigger choice). (4) **The place is the host's beat at the end of the block**, since that is where a modulator that goes by itself puts its output, and the tempo inside a block is taken to be the block's. (5) **A bar is four beats** (the sync table's own assumption: a session has no time signature). (6) **The transport's play, stop and loop are not read**: a pattern is not started by the host, and nothing is reset when it plays; a TODO. (7) **A flag in the snapshot's meta** (`hostTempo`, left out of the wire while false) and a new snapshot when it first becomes true, so that the page's bar shows the host's number and no field: no new message, no new event. (8) **The file keeps the tempo that the host had last** (`bpm`), which is not what plays: the host says it again at the next block.

**Decisions of step 120 (D120; the user may overrule them).** (1) **A CLAP plugin is told the tempo and no more**: no `IS_PLAYING`, no position. Tang does not know whether a host plays unless the host's transport is passed on, which is a step of its own; a plugin that waits for `IS_PLAYING` does not run, as before, and one that only wants the tempo has it. VST3's process context goes on saying that the plugin plays, as it always did: the two formats were not made alike by changing what VST3 plugins have been told. (2) **Every plugin is told every block**, not when the tempo changes and not when a plugin comes in: one call that stores a number, for each plugin, with no memory in the graph of who was told what, and a plugin that comes in later needs no case of its own. (3) **A tempo that is not a tempo is not told, twice**: the graph does not take one (`set_host_time`, `SetGlobalBpm`) and the adapters do not keep one, so that a caller that is not the graph cannot give a plugin a NaN. (4) **LV2 is left out**: its tempo is a `time:Position` atom in the event sequence, a different piece of work, and nothing of the user's is LV2. (5) **The beat and whether the host plays are not passed on**: the user asked for the BPM, and a hosted sequencer that starts and stops with the DAW is a behaviour to be asked for.
